# A production `jarvis` on PATH

GitHub issue 757, "`jarvis` is not on PATH, and the obvious fallback drives the dev
instance". Work order wo-2ae8ca92. Design decided by Neo on questions q1413 and q1414
(Option A / A1); this spec states the mechanism, it does not re-open the choice.

## The problem

**Root cause, one sentence:** every piece of production's identity — `JARVIS_HOME`,
`PRODUCTION_CODE`, `JARVIS_ENV` — lives *only* inside the two systemd units
(`deploy/jarvis.service.template:12-15`, `deploy/jarvis-ui.service.template`), so it
reaches the daemon and the workers it spawns and reaches **nothing a human types**. There
is no install step that puts a production `jarvis` on an interactive PATH, so the two
things a user actually does both fail, and the second fails *silently*.

### The two failures, traced

1. **`jarvis` in an ordinary login shell: command not found.** The production CLI is the
   console script inside the deployed venv, `$PRODUCTION_CODE/jarvis_os/.venv/bin/jarvis`
   (`deploy/jarvis.service.template:19`, and the precondition
   `scripts/install_prod_service.sh:40-42` which refuses until that file is executable).
   `install_prod_service.sh:50` puts that directory first on the *service's*
   `Environment=PATH=`, and that is the only place it is ever added. Nothing writes to
   `~/.local/bin`, nothing appends to a shell rc file. The deployed venv is not activated
   by anything.

2. **The obvious fallback drives the WRONG FLEET, with no error.** Typing the full path,
   `~/workspace/production/jarvis_os/.venv/bin/jarvis status`, runs production *code*
   against the *development* state: `paths.jarvis_home()` is
   `Path(os.environ.get("JARVIS_HOME", "~/.jarvis"))` (`src/jarvis/paths.py:30-31`), so
   with `JARVIS_HOME` unset — which is exactly what an interactive shell has — every read
   and write lands in `~/.jarvis`, the dev instance's home. `CentralStore`/`NeoStore`
   resolve their paths at construction (`mem:testing`, `tests/test_state_isolation.py`),
   so there is no later point at which the mistake can be noticed. The dashboard's
   prod/dev badge cannot help either: `paths.deployment_env()`
   (`src/jarvis/paths.py:40-66`) keys on `JARVIS_ENV` first and the code's *location*
   second, so this invocation reports **`production`** (the code genuinely is under
   `$PRODUCTION_CODE/jarvis_os`) while writing dev state. A mislabelled instance is worse
   than an unlabelled one.

The asymmetry is the whole defect: `deploy/*.service.template` carries three
`Environment=` lines, and the machine's humans carry none of them.

### Why nothing caught it

`jarvis doctor` has an invariant for a stale *unit* (`INV-SERVICE-PATH`,
`src/jarvis/invariants.py:3880-3923`) and one for a dirty production *checkout*
(`INV-PROD-CLEAN`, `:3926-3983`), both born from the same lesson — a one-time manual
install step that nothing ever re-ran or compared (issues #41, #90, #202). The
interactive CLI is a *third* instance of that lesson and has no installer to drift from
yet, so there was nothing to check.

## The fix

Three pieces, one per layer that already exists for the units: a renderer, a call from
the deploy, and a doctor invariant. Nothing in the daemon.

### 1. `deploy/jarvis.cli.template` + `scripts/install_prod_cli.sh`

**Where and why there.** `deploy/` holds the rendered-artifact templates and
`scripts/install_prod_*.sh` holds the one-time idempotent installers that render them
with `sed -e "s#@PLACEHOLDER@#…#g"` (`scripts/install_prod_service.sh:65-75`). A wrapper
is the same kind of object as a unit — a file whose content is a function of `PROD_ROOT`
— so it belongs in the same pair of places, under the same `@PLACEHOLDER@` convention. A
separate script rather than a flag on `install_prod_service.sh`: that script's whole body
is about systemd (PATH probing, `daemon-reload`, `enable`, the cgroup-safe restart
order), and the wrapper needs none of it and must never trigger a restart.

**Exact wrapper text.** `deploy/jarvis.cli.template`, verbatim:

```bash
#!/usr/bin/env bash
# Jarvis OS production CLI — generated by scripts/install_prod_cli.sh. DO NOT EDIT.
# Rendered from deploy/jarvis.cli.template; re-run the installer to update it.
#
# The three exports below are the SAME values deploy/*.service.template carry
# (jarvis.service.template:12-15), so a command typed in a shell and a command the
# daemon runs reach ONE fleet. Without them `jarvis` runs production code against
# ~/.jarvis, the dev instance's home (src/jarvis/paths.py:30-31) — issue 757.
export JARVIS_HOME="@PROD_ROOT@/state"
export PRODUCTION_CODE="@PROD_ROOT@"
export JARVIS_ENV=production
exec "@PROD_DIR@/.venv/bin/jarvis" "$@"
```

`@PROD_ROOT@` is `$PRODUCTION_CODE` and `@PROD_DIR@` is `$PROD_ROOT/jarvis_os`, named
and derived exactly as in `install_prod_service.sh:35-37`. The paths are quoted (a unit's
`Environment=` is not, but this is shell). `exec` keeps the wrapper out of the process
tree and passes the exit status through. `"$@"` not `$*`.

The generated-marker comment line is load-bearing: it is how the invariant tells *our*
wrapper from some other `jarvis` on PATH.

**`scripts/install_prod_cli.sh`**, mirroring `install_prod_service.sh` in shape:

* `set -euo pipefail`; `REPO` from `git -C "$(dirname "${BASH_SOURCE[0]}")" rev-parse
  --show-toplevel`; `PRODUCTION_CODE="${PRODUCTION_CODE:-$HOME/workspace/production}"`.
* **Precondition, same shape and same message as `install_prod_service.sh:40-42`:**
  `[ -x "$PROD_DIR/.venv/bin/jarvis" ]` or exit 1 with `production not deployed yet
  ($PROD_DIR/.venv/bin/jarvis missing) — run scripts/shipit.sh first`. A wrapper that
  `exec`s a missing file is a `jarvis` that reports `No such file or directory`, which is
  worse than `command not found`.
* Flags: `--dry-run` (print the plan and the rendered body; write nothing) and
  `--bin-dir <dir>` for the target directory, defaulting to
  `${JARVIS_CLI_BIN_DIR:-$HOME/.local/bin}` — the same seam `--unit-dir` gives the unit
  installer, and the same env var the invariant reads (§4).
* `mkdir -p "$BIN_DIR"`, render to `$BIN_DIR/jarvis`, `chmod 755`, print
  `installed $BIN_DIR/jarvis`. Idempotent by construction: the output is a pure function
  of `PROD_ROOT`, so a second run rewrites the same bytes.
* **Say it out loud when `$BIN_DIR` is not on the caller's PATH** — in the character of
  the `gh`-reachability note at `install_prod_service.sh:85-91`, and for the same reason:
  the install succeeds either way and the only symptom is a feature that silently never
  happens. Message names the directory and says to add it to the shell rc file.

**It must not shadow dev, and does not.** Dev runs `uv run jarvis` from inside
`~/workspace/agentic_os` (`docs/DEPLOYMENT.md:17`), which resolves the console script in
that checkout's own `.venv` and never consults `PATH` for `jarvis` at all. And a Jarvis
*worker* gets the unit's PATH, whose first entry is `$PROD_DIR/.venv/bin`
(`install_prod_service.sh:50`, guarded by
`tests/test_install_prod_service.py:112-118`) — ahead of `$HOME/.local/bin`, which is in
the fallback list at `:57`. So a worker's `jarvis` keeps resolving to the venv binary
directly, with the environment it already inherits. Nothing regresses; the wrapper only
changes what an *unconfigured* shell resolves.

### 2. `scripts/shipit.sh` — rendered on every deploy, not once

**Where and why there.** Immediately after the unit re-render in step 5a and **before**
step 5b (`scripts/shipit.sh:402-435`, `:436`). Step 5a exists because a one-time manual
render let the #41/#90 fix sit unapplied for a release and a half; the wrapper names
`@PROD_DIR@`, so it is stale in exactly the same way and wants exactly the same cure.
Before 5b because the staged path exits at `:446` — a `--stage` release must get the
wrapper too.

```bash
CLI_INSTALLER="$PROD_DIR/scripts/install_prod_cli.sh"
if [ ! -f "$CLI_INSTALLER" ]; then
  say "NOTE: $CLI_INSTALLER is missing in $TAG — the \`jarvis\` wrapper was NOT"
  say "      re-rendered. Check with: jarvis doctor (INV-PROD-CLI)"
else
  say "re-rendering the production \`jarvis\` wrapper from $TAG"
  run "'$CLI_INSTALLER' || say 'NOTE: wrapper install failed — jarvis doctor (INV-PROD-CLI)'"
fi
```

Three properties, each deliberate:

* **Run from `$PROD_DIR`**, like step 5a's `INSTALLER` at `:423`, so the wrapper matches
  the tag just deployed rather than the dev tree shipping it.
* **Best-effort.** A tag old enough to predate the script is a legal thing to deploy and
  must not abort a release — the same judgement, and the same `say` NOTE, as `:426-431`.
  The `|| say …` rides inside the `run` string because `run` is `eval` under `set -e`
  (`:95`); in `--dry-run` the whole string is merely printed.
* **No restart, no systemd call at all.** The wrapper is read at the next `jarvis` the
  user types; a running daemon is unaffected, so this cannot disturb steps 6 and 8.

**Departure from 5a worth stating:** 5a renders only when the units are *already*
installed (`unit_installed`, `:415-418`), because installing a service on a machine that
never had one is a decision shipping should not make. This call is **unconditional**. A
`~/.local/bin/jarvis` enables nothing, starts nothing and survives nothing; and the only
machine that reaches step 5 is one where production was just deployed, which is precisely
the machine on which `jarvis` must mean production. The script's own precondition is the
guard that matters.

### 3. `INV-PROD-CLI` — a doctor-only invariant

**Where and why there.** `check_prod_cli` in `src/jarvis/invariants.py`, next to
`check_service_path` and `check_production_clean`, registered in `OS_INVARIANTS`
(`:4270-4278`). It is the third member of that family and mirrors
`check_service_path:3880-3923` in character, point for point:

* **Reads the FILE**, not the environment. What is on disk is what the next invocation
  uses; reading `os.environ` would report nothing, because a session that *has* the
  variables (a worker, the daemon) is not the session that is broken.
* **Report-only, and explicitly NOT repairable.** `check_os` (`:4281-4292`) is
  "read-only by construction" and `OS_INVARIANTS` has no repair facility — do not add
  one. Writing an executable onto the user's PATH is an install action, not a derivation.
* **Doctor-only.** In `OS_INVARIANTS`, never in `INVARIANTS` (`:4459`), per
  `check_config_drift`'s reasoning: the reconcile tick must not file an inbox item every
  few seconds about a file only a human can install.
* **The detail names the way out** — `scripts/install_prod_cli.sh` — the way
  `INV-SERVICE-PATH` names `install_prod_service.sh`.

**New helpers in `src/jarvis/release.py`**, beside `UNIT_DIR_ENV` / `unit_dir` /
`unit_environment` (`:96-123`), because that is already the module that answers "what is
installed on this machine" and the invariant should not learn to parse files itself:

```python
CLI_BIN_DIR_ENV = "JARVIS_CLI_BIN_DIR"     # mirrors UNIT_DIR_ENV, same reason
def cli_bin_dir() -> Path                   # $JARVIS_CLI_BIN_DIR or ~/.local/bin
def cli_wrapper() -> Path                   # cli_bin_dir() / "jarvis"
def cli_wrapper_facts() -> dict | None      # None if unreadable/absent
```

`cli_wrapper_facts` returns `{"generated": bool, "target": str | None, "env": {name:
value}}` parsed from the file text: `generated` is whether the marker comment
`generated by scripts/install_prod_cli.sh` is present, `target` is the argument of the
`exec` line with quotes stripped, `env` the `export NAME="value"` lines — tolerant in the
same way `unit_environment` is (an absent or unreadable file is `None`, not an error).

**Firing conditions.** The precondition first, then three reports:

| Condition | Verdict |
|---|---|
| `not (production_code_dir() / ".git").exists()` or `$PROD_DIR/.venv/bin/jarvis` not executable | **silent** — no production deployment on this machine |
| wrapper absent | report **missing** |
| wrapper present, no generated-marker | report **foreign** |
| `target != str(production_code_dir() / ".venv/bin/jarvis")` | report **wrong checkout** |
| `env["JARVIS_HOME"] != f"{production root}/state"` | report **wrong home** |

The precondition is `INV-PROD-CLEAN`'s precedent (`:3953-3955`, "no production deployment
on this machine") tightened by the deployed-venv test the installer itself uses, and it
is what keeps the check meaningful: a dev-only machine has nothing to report, and a
machine where the deploy exists but the wrapper does not is the exact state issue 757
describes. Note that it does **not** key on `paths.deployment_env()` — that answers
"which instance am I", and the subject here is the machine's interactive shell, which is
neither instance. `jarvis doctor` run from the *dev* checkout on a host that also runs
production therefore does report, and must: that is the host, and that is the human.

"Foreign" is reported rather than ignored because a `jarvis` on PATH that is not ours is
the defect's second half — most likely a dev install pointing at `~/.jarvis` — and the
whole point is that typing `jarvis` must not silently reach the wrong fleet. The detail
says it was not generated by the installer, so a user who installed one deliberately can
read the report and decide.

**Detail messages.** Missing:

> `no production `jarvis` on PATH: {wrapper} does not exist, so `jarvis` in an
> interactive shell is either command-not-found or — worse — the venv binary with no
> `JARVIS_HOME`, which drives the DEV instance at ~/.jarvis silently (issue 757). Install
> it with scripts/install_prod_cli.sh (it starts and restarts nothing).`

Wrong checkout / wrong home, one message with the offending pair substituted:

> `{wrapper} execs {target} and exports JARVIS_HOME={home}, but production on this
> machine is {prod_dir} with JARVIS_HOME={expected_home} — every `jarvis` typed in a
> shell is therefore driving a different fleet from the one the units run. Re-render it
> with scripts/install_prod_cli.sh.`

`context` carries `{"wrapper": str, "target": str | None, "jarvis_home": str | None,
"expected_target": str, "expected_home": str, "generated": bool}`, so the whole
comparison is machine-readable without re-reading the file.

### 4. Test isolation — a new gated env var

The check reads `~/.local/bin`, **outside `$JARVIS_HOME`**, which is precisely the trap
kn-38b98594 records and which `release.UNIT_DIR_ENV` and `paths.PRODUCTION_ROOT_ENV`
already pay for (`src/jarvis/testing.py:132-143`): left ambient, `jarvis doctor` tests
pass or fail on the state of the developer's own machine — and on this host they would
*fail*, on the very defect the check exists to report.

So `release.CLI_BIN_DIR_ENV` is honoured by **both** halves — `release.cli_bin_dir()` and
`install_prod_cli.sh`'s `--bin-dir` default — and is added to `gate_environment`
(`src/jarvis/testing.py:114-151`) alongside those two:

```python
# The developer's own ~/.local/bin, which `INV-PROD-CLI` reads. Same trap as the two
# entries above: left ambient, `jarvis doctor` in a test passes or fails on whether the
# human has run install_prod_cli.sh — and it fails, which is the subject of that check.
# Pointed at an empty directory inside the sandbox: no wrapper installed, and
# PRODUCTION_ROOT_ENV above already means "no production deployment", so the check is
# silent either way.
release.CLI_BIN_DIR_ENV: str(root / "cli-bin"),
```

Both guards are needed, not one: the sandbox's `PRODUCTION_CODE` makes the precondition
false *today*, and a future test that builds a fake deployed production under `tmp_path`
would otherwise start reading the real `~/.local/bin`.

### Test plan

Shell scripts are tested here by driving the real script with `--dry-run` against
`tmp_path` (`tests/test_install_prod_service.py:43-50`, `tests/test_shipit.py:9-11`, and
the "testing shell scripts" knowledge topic). Same idiom, same file layout: the wrapper
tests and the invariant tests live together in **`tests/test_install_prod_cli.py`**, the
way `test_install_prod_service.py` keeps `INV-SERVICE-PATH` beside the script it watches.

**The wrapper** (`prod` fixture copied in character from
`tests/test_install_prod_service.py:32-40`; env is `HOME`, `PRODUCTION_CODE`, `PATH`,
plus `--bin-dir tmp_path/bin`):

1. renders an executable `bin/jarvis` whose `exec` line is
   `$PROD_DIR/.venv/bin/jarvis "$@"`, mode `0o755`.
2. **the three exports equal the unit's three `Environment=` values** — render the
   wrapper *and* the units from the same `PRODUCTION_CODE`, parse both, assert
   `JARVIS_HOME`, `PRODUCTION_CODE` and `JARVIS_ENV` match pairwise. This is the contract
   in §1 made mechanical; drift between the two files is the only way this feature breaks
   quietly.
3. refuses when production is not deployed: non-zero exit, `not deployed yet` in stderr,
   and nothing written to the bin dir.
4. `--dry-run` prints the plan and writes no file (and nothing under `HOME`).
5. idempotent: two runs, byte-identical output, exit 0 both times.
6. warns on stderr when the bin dir is not on the invoking PATH, and does not warn when
   it is.
7. `bash -n` on the rendered wrapper, and a smoke run of it with a stub `jarvis` in the
   fake venv asserting the stub saw `JARVIS_HOME` and the forwarded argv (including an
   argument containing a space — the `"$@"` guarantee).

**The shipit call** (extend `tests/test_shipit.py`, `--dry-run` against the throwaway
repo):

8. the dry-run plan contains `install_prod_cli.sh`, and its line precedes the staging
   marker line, proving it is before 5b.
9. a `$PROD_DIR` whose `scripts/` lacks the installer prints the `NOTE:` naming
   `INV-PROD-CLI` and the release still exits 0.

**The invariant** (fixture sets `JARVIS_CLI_BIN_DIR` and `PRODUCTION_CODE` to a fake
deployed prod under `tmp_path`, mirroring `test_install_prod_service.py:195-274`):

10. wrapper missing → exactly one `INV-PROD-CLI`, detail contains
    `scripts/install_prod_cli.sh` ("no way out is named" is the existing assertion).
11. a wrapper the real script just rendered → silent. Rendered, not hand-written: it
    closes the loop between the two halves.
12. wrapper exec'ing a different checkout → violation, `context["target"]` is the wrong
    path.
13. wrapper exporting a different `JARVIS_HOME` → violation (target correct, so this
    proves the home is checked independently).
14. a hand-written `jarvis` without the marker → violation, `context["generated"]` false.
15. no production deployment (`PRODUCTION_CODE` at an empty dir) → silent, even with no
    wrapper anywhere. This is every dev-only machine.
16. doctor-only: `check_prod_cli in OS_INVARIANTS` and `not in INVARIANTS`.

**The sandboxing** (extend `tests/test_isolation_gate.py`):

17. `gate_environment(root)[release.CLI_BIN_DIR_ENV]` is inside `root`.
18. under the gate, `release.cli_bin_dir()` resolves inside `testing.GATE_ROOT` and
    `check_prod_cli()` is silent — so a suite running under the gate can never read the
    real `~/.local/bin`.

## Out of scope

* **Daemon self-heal — ruled out by Neo (q1413/q1414).** The daemon will not install or
  repair the wrapper. It is a write outside `$JARVIS_HOME` onto the user's PATH, and the
  reconcile tick is not where an install belongs. `INV-PROD-CLI` reports; a human runs
  the script.
* **A repair facility for `OS_INVARIANTS` — ruled out.** `check_os` is read-only by
  construction and both its neighbours say in their docstrings why they are not
  repairable. Do not add a repair hook to make this one self-fix.
* **Shell rc files.** Nothing appends to `~/.bashrc` or `~/.profile`. The wrapper goes in
  a directory that is conventionally already on PATH, and the script *says so* when it is
  not, rather than editing a file it does not own.
* **Changing how dev runs.** `uv run jarvis` stays the dev invocation; no dev wrapper, no
  `jarvis-dev`.
* **A `--home`/`--env` flag on the CLI.** A per-invocation flag would make the fleet a
  thing you can target wrongly in one keystroke. The decided design is one `jarvis` that
  means production.

## Rejected alternatives

* **A symlink `~/.local/bin/jarvis -> $PROD_DIR/.venv/bin/jarvis`.** Simplest, and it
  fixes only failure 1. The exec'd binary would still run with no `JARVIS_HOME` and so
  still drive `~/.jarvis` — it converts a loud `command not found` into the silent wrong
  fleet, which is the worse half of the defect. A wrapper exists for the three exports,
  not for the PATH entry.
* **`uv tool install` / `pipx install` of the deployed tree.** Installs a *second* copy of
  the code, so the thing on PATH is no longer the thing the units run and `jarvis
  --version` can disagree with production. It also carries no environment, so failure 2
  survives.
* **Export the three variables from `~/.profile` instead.** Fixes failure 2 and makes
  every shell on the machine, including the one a dev session uses, silently point at
  production state. The variables belong to one command, not to the login session.
* **A `shell.nix`-style `activate` script the user sources.** Needs a human to remember a
  step before every use; the failure mode is the current one, unchanged.
* **Put the invariant on the reconcile tick so the user hears about it without running
  `doctor`.** Same reasoning `check_config_drift` and `check_service_path` already
  recorded: an inbox item every few seconds about a file only a human can install is an
  alarm nobody reads. `jarvis doctor` runs the OS invariants, and the daemon runs the
  same checks per tick for the project-level set only.
* **Teach `install_prod_service.sh` a `--with-cli` flag instead of a second script.** That
  script's every line is systemd, and its restart path can SIGTERM the session running it
  (`:113-136`). Folding a PATH install into it means the wrapper cannot be re-rendered
  without touching services — which is exactly what step 5a's `--no-restart` dance exists
  to avoid.
