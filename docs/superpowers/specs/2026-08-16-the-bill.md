# The bill: every token an order spent, itemised and reconciled

*wo-4576667e, 2026-08-16. Third of the token-accounting notes, after
`2026-08-16-what-jarvis-spends-on-itself.md` (the OS's own calls) and
`2026-08-16-what-a-worker-spends-below-itself.md` (the worker's subprocesses). Those two
made the spend VISIBLE. This one makes it READABLE, and corrects the tokens.*

## What was wrong

The work order page said this, and every figure on it was correct:

```
~$1.81 · worker ~$1.66 · jarvis ~$0.15 / 2 calls · 1.2M in / 14k out · 2 turns ·
re-write tax ~$0.28
```

The user, who owns the OS, asked four questions of it:

1. Why is the OS's half all called "jarvis" — was nothing spent on anything else?
2. What is a re-write tax?
3. Is the 1.2M worker + jarvis, or just the worker?
4. Why is there no token count per worker and per OS?

Question 3 had a real defect behind it: the dollar figure was the whole order and the
token figure beside it was the worker's alone. The other three are the same complaint —
a line of totals is not an account of anything. You cannot expand it, you cannot check
it, and it never says what it leaves out.

## The measurement that changed the foundation

Before building the surface, the turn accounting was measured against the raw result
files. `claude_cli.derive_turn_usage` took a turn's token totals from the result
envelope's top-level `usage` object. **That object is not the turn's total.**

Over the 186 live result files carrying both, `usage` runs at 33–60% of `modelUsage`:

| work order | `usage` (recorded) | `modelUsage` | transcript, derived independently |
|---|---|---|---|
| wo-cd73c537 | 11.67M billed input | 17.685M | 17.685M |
| wo-67d4f8b0 | 9.95M billed input | 29.932M | 29.932M |

`modelUsage` agrees with the session transcript **to the token** — two independent
sources, one of them the file `usage.py` has always read — and its `costUSD` sums to
`total_cost_usd` to the cent. Dollars were therefore never wrong (they come from
`total_cost_usd`); every token figure the OS had recorded was.

Neo ruled (question 121) to take the totals from `modelUsage` and to re-derive already
persisted envelopes on read behind a version marker, accepting that every historical
token figure rises. `USAGE_SCHEMA_VERSION` is that marker; `ops._turn_usage` re-derives
a version-1 row wherever the outfile survives, keeps and flags it where it does not, and
the flag is rendered ("counted the old way") so a re-derived order is distinguishable
from a pre-fix one.

`modelUsage` counts subagents — which is *why* it matches the transcript, since
`read_session` reads the subagent files too. So subagents are a SHARE of the worker's
line, never an addend.

## The shape: one set of charges, folded two ways

`jarvis/bill.py` builds a flat list of `Item`s — the indivisible facts, each a token
count with a model, a price, an owner and a turn — and folds it twice:

```
by actor                              by turn
  worker → turn 1..n                    turn 1 → worker, jarvis, subprocesses
  jarvis → Neo, panel seats, digests    turn 2 → …
  subprocesses → pytest, …              outside any turn
```

Both views are folds of the same leaves, so "add up the turns and you get the order" is
true by construction rather than by a second calculation that could disagree. Every
parent line is the sum of its children because it is accumulated from them.
`bill.reconcile` proves all of it on every payload and the result is rendered on the
page: an accounting nobody can check is a claim, not an account.

**Attribution** (also ruled on question 121): an `agent_calls` row belongs to the last
turn that had STARTED at or before its timestamp. That puts a Neo answer on the turn that
asked the question — a worker asks and ends its turn, so the answer is paid for while
nothing is running — and a subprocess call on the turn that ran it. Anything earlier than
the first turn lands on an explicit `outside any turn` line rather than being absorbed.

**The gap line.** A work order with some turns recorded and some pruned charges the
difference between the transcript and the recorded turns as its own line, per class,
clamped at zero. Without it a bill silently loses however much of itself the pruning took.
The same line is labelled "still running" when the missing turn is simply live, because a
turn writes its result JSON when it ends.

## The TTL is a price

A cache WRITE is 1.25× base input at the 5-minute TTL and **2× at the one-hour** one
(kn-f94abf34); a read is 0.1× under either. `usage.py` priced every write at 1.25×, which
understates the largest avoidable line on the bill by up to 60% of itself for every write
made before `FORCE_PROMPT_CACHING_5M` shipped. The ephemeral split is now read from both
sources — per message in a transcript (exact) and per turn in an envelope (a sample whose
RATIO carries) — and `usage.class_costs` prices each class separately. On wo-cd73c537 the
list estimate moved from $27.08 to $34.23 against the CLI's own $33.23.

That per-class breakdown is what makes it a bill: quantity × rate = amount, four lines,
and the re-write tax stops being a mystery figure — it is the part of the cache-write line
that paid to send context a warm cache would have served at a tenth of the price.

## The surfaces

* `/cost/<project>/<id>` is the bill, for a work order **or a feature order** (a feature
  expands into its orders, each into its turns). It replaces the old per-turn drill-down.
* The work order page keeps **two numbers and a link** — total tokens, total dollars,
  "details →" — plus the turn-by-turn bill lower down and, on each message, what the turn
  it started cost.
* `jarvis cost <id>` renders the same payload in the terminal. One payload behind both,
  or a user reading the terminal and a user reading the page are told different things.
* Both state what is NOT on the bill: the classes that spent nothing, calls made outside
  Jarvis's transport (the floor), and the user's own Jarvis sessions.

## What is measured

* `tests/test_bill.py` — the identities: both views sum to the total, every parent is its
  children, no charge appears twice, subagents are not added, the clamp holds.
* `evals/test_bill_accounting.py` — the bill against ground truth summed **independently**
  out of `wo_turns`, `agent_calls` and the transcript, through the real dispatch path. An
  eval that re-derived the total the way the code does could only prove the code agrees
  with itself.
* `evals/llm/test_bill_comprehension.py` — the four questions above, put to a model that
  has nothing but the rendered bill. The surface was not rewritten because it was wrong;
  it was rewritten because it was unreadable, and no unit test can fail for that.
* The fake `claude` CLI now reports `modelUsage` LARGER than `usage`, in the proportion
  the real one does. Every fixture having them equal is what let the wrong one be read for
  months: no test could tell which was being used.
